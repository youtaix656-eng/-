# Ouro — 自分専用のAI会社

> 「AIを使うのではなく、AIを雇う。」
> 「AIが働くほど、あなたの知識が資産になる。」

公開先：https://youtaix656-eng.github.io/-/ouro

Ouro はAIチャットアプリではありません。**あなたがオーナーの会社**です。
AI社員に仕事を依頼すると、社員どうしで引き継ぎながら仕事を進め、
その成果が**会社の知識資産**として積み上がっていきます。

```
情報 → 収集 → 整理 → 検証 → 保存 → 活用 → 新しい成果 → 再び知識へ
```

## AIエンジンについて（お金をかけずに始める）

Ouro は**サーバーを持ちません**。月額費用はゼロです。

- **キーが1つも無くても全機能が動きます。** その場合は「ローカル社員」が
  仕事の型（チェックリスト）を組み立てます。AIではないことは画面に明記されます。
- 実際に社員に考えさせるには、設定でAPIキーを1つ登録します（BYOK）。
  無料枠のある Gemini から始めるのが最も費用がかかりません。
- キーは端末の IndexedDB にのみ保存され、**バックアップの書き出しにも含まれません**。
- 費用は仕事ごと・社員ごと・累計で常に表示されます（隠しません）。

## 役職 × ジャンル × 3席

社員は3つの軸で並ぶ。

- **役職**（15種）… 何ができるか。リサーチャー／アナライザー／…
- **ジャンル**（9種＋追加できる）… どの分野で。汎用／医療・健康／副業・お金／…
- **席**（既定3席）… 同じ組でも持ち味が違う。主席＝網羅／次席＝速さ／三席＝別視点

1つの組（役職 × ジャンル）につき**3席まで**。同じリサーチャーでも、医療の調査が得意な3人と
副業の調査が得意な3人を別に雇える。席番号は組の中で数えるので、別ジャンルの席が埋まっていても
番号は1から始まる。3席を超えて増やすこともできる。

依頼するときに分野を選ぶと、その分野の社員が優先して担当する（いなければ汎用の社員が受ける）。

## AIキャラクター（会社チーム）

役職は2つのチームに分かれる。

- **知識チーム**（15役職）… 調べる・整理する・確かめる・作る。Ouro の元からの役職。
- **会社チーム**（10役職）… 事業を回す。①プロダクトオーナー ②臨床監修者 ③AIプロンプト設計者
  ④コンテンツマーケター ⑤営業 ⑥カスタマーサポート ⑦エンジニア ⑧データ分析担当
  ⑨経理・労務 ⑩広報・ブランディング。

会社チームの各役職には**名前つきのキャラクターが3名ずつ（全30名）**いる。
自動では雇わず、「AIキャラクター名鑑」から1名ずつ、または役職ごとにまとめて雇う。

肖像は**線画のSVGをその場で描く**（画像ファイルを持たないのでオフラインでも軽い）。
この方針は 2026-08-25 に確認済みで、**イラスト画像への差し替えはしない**。
**顔立ちで人種・民族を描き分けてはいない**——少ない線でそれをやると戯画になるため、
見分けは髪型・装い・紋章でつけ、出身は人物像の文章として持たせている。

責任の重い役職には、できないことを明記してある。臨床監修者は**診断をしない**、
経理・労務は**税務・労務の最終判断をしない**。どちらも確認すべき点を挙げるまでが仕事で、
最終判断は専門家とあなたが行う。

## マーケティングチーム（5人体制）

3つめのチーム。**攻めと守りを同じ役職に兼務させない**ことが核。

| 担当 | 名前 | 性質 | 決まり |
|---|---|---|---|
| 企画・コンテンツ | Olivia | 攻め | 成果物は必ず Ethan の確認を通す |
| 分析・ガバナンス | Ethan | 守り | 承認／差し戻しの権限。**KPIを持たない** |
| 運用・配信 | Sofia | 攻め | 予算上限に近づいたら Ethan に委ねる |
| ブランド・PR | Lucas | 対外 | 対外発信の前に Ethan の確認 |
| 予測・戦略分析 | Mia | 助言 | 提案のみ。予算執行も施策実行もしない |

これは文章だけの約束ではなく、**動きとして実装している**。

- 攻めの担当（Olivia / Sofia / Lucas）に依頼すると、**Ethan の確認が自動で最後に入る**。
- 確認は `maxSteps` で切り落とさない。「上限に達したので確認を省いた」が起きてはいけないため。
- Ethan を雇っていないまま攻めの担当に依頼すると、結果画面が
  **「確認を通していない成果物です」**と警告する（黙って公開させない）。
- Ethan に成果目標（KPI）を持たせない。持たせると自身が攻め化し、ブレーキが甘くなる。

チーム共通のルールは、個別の役割より**先に**読ませている。

なお Olivia / Ethan / Sofia / Lucas は、会社チームの Olivia Bennett・Ethan Clarke・
Sofia Marchetti・Dr. Lukas Weber と名前が近い。指定どおりの名前を使うと決めてあるので
（2026-08-25 確認済み）、姓を足して区別することはしない。画面ではチーム名と役職を
併記して取り違えを防いでいる。

## 仕事台帳（受け渡しの形）

AI社員をいくら増やしても、受け渡しの形が無ければチームにならない。台帳は
「受け付けた仕事を1枚で見る」ための画面で、記事でいう共通記憶にあたる。

- **台帳は手で更新しない。** 表計算の台帳は人が更新する前提だが、Ouro は仕事が
  実際に走る場所なので、同じ設計にすると更新漏れで台帳が嘘をつく。
  列は仕事から毎回導き（`lib/ledger.js`）、人が持つのは
  **期限・次の対応・保留理由の3つだけ**。置き場所は仕事の側（`task`）。
- **受付番号は採番の表を持たない。** 受け付けた日と id の末尾から毎回同じ番号を作る
  （`ticketOf`）。番号の表を持つと、それが第2の正になる。
- **状態は5つ**（未着手・作業中・確認待ち・保留・完了。ほかに 止まっている／中止）。
  **保留は理由が必須**で、保留中は実行のボタンを出さない（`isRunnable`）。
- **「今日やること」** ＝ 期限切れ・今日まで・あなたの判断・止まっているもの
  （`todayFocus`）。ホームと台帳が同じ関数を使う。
- **CSV** は Excel との橋渡し（`lib/csv.js` / `lib/ledgerCsv.js`）。
  セルを数式にさせない・BOM を付ける・**CSV から仕事は作らない**
  （受付番号が一致した仕事の3列だけを書き換える）・**読めない日付で今の期限を消さない**。

### 回答の形と、あなたの判断

- 会社としての提出物は5項目（①結論 ②最優先事項 ③あなたの判断が要ること
  ④成果物 ⑤担当と期限つきのTODO）。**枠を掛けるのは最後の手順だけ**
  （`lib/outline.js` / `runtime.isFinalStep`）。
- ③の中身は `lib/decisions.js` が1行ずつ拾って「判断待ち」にする。**AIは呼ばない**ので
  費用はかからない。決めるまで台帳では「確認待ち」のまま。
- 承認（実行してよいか）と判断（出てきたものをどうするか）は**別の層**。
- 外へ出す前に `lib/guard.js` が「保証します」「3日で納品」「100%」などを知らせる。
  止めはしない——価格・納期・効果の確約は、AIではなく人が引き受けるところだという合図。

## 目次（索引）

リポジトリ共通の「目次・索引のルール」をそのまま実装している。

1. 並びは **あ〜ん → A〜Z**。読み（ひらがな）で並べ替える。
2. **数字も読み方で振り分ける**（「20歳未満」→ にじゅう… → な行）。
3. **読みは明示、自動推定しない。** 漢字の読みは推測せず、読みが無い項目は
   「その他」の枠に出して入れ忘れが見えるようにする。
4. **タイトルは重複させない**（`test/toc.test.mjs` が機械チェック）。
5. 文字は大きめ、タップで該当箇所へ飛ぶ（飛び先は固定ヘッダーの下に出して一時的に光らせる）。

目次は `data/toc.js` が各データから**自動生成**する（書き写さない）。
役職を1つ足せば目次にも自動で並ぶ。

## カレンダー

- 月のマスに**実績**（● 完了した仕事／◆ 増えた知識）と**予定**（▲ 締切／■ 自分の予定）が出る。
- 締切は `deals` から毎回導く。**予定に複製しない**ので、締切を直せばカレンダーもすぐ追従する。
- 締切から逆算して「いつ着手すべきか」を出す（締切日にいきなり始めさせない）。
- 月の集計（仕事・知識・入金・AI費用）も出る。

## 設計上の約束（変えるときに壊さないための決まり）

1. **AI社員（人格・役割・記憶）とAIエンジン（Claude/GPT/Gemini）は分離する。**
   社員は `providerPref`（希望）だけを持ち、エンジンの実体を持たない。
   モデルが入れ替わっても社員データは無傷。
2. **出典のない知識を作らせない。** `createKnowledge()` は出典が空なら
   「AI生成（未検証）」の擬似ソースを自動で立てる。
3. **既定の権限は最小。** 送信・削除・支払い・外部公開は必ずユーザー承認を通る。
4. **接続数の上限をハードコードしない。** 判定は `plans.connectionLimit()` の1か所だけ。
5. **役職を足すときは `data/roles.js` に1件足すだけ。** 画面は直さない。
6. **保存キーは `storage.KEYS` に登録する。** 直接 `idbSet` を呼ばない。
7. **漢字の読みを推定しない。** 目次に載るデータには `reading` を必ず持たせる。
8. **席番号は組（役職×ジャンル）の中で数える。** 役職だけで数えると番号が飛ぶ。
9. **締切をカレンダーの予定に複製しない。** `deals` から導く（二重管理を作らない）。
10. **肖像で人種・民族を描き分けない。** 見分けは髪型・装い・紋章でつける。
11. **未雇用の役職を計画に入れない。** 担当者が見つからず仕事全体が失敗する。
12. **攻めと守りを同じ役職に兼務させない。** 承認する側が承認される側を兼ねない。
13. **承認の手順を上限で削らない。** 安全のための手順なので、常に最後に残す。
14. **費用の出る実行は、仕事も会議も同じ扱い。** 会議だけ承認を飛ばさない
    （いちばん高いのは会議：AIを「人数×2＋1」回呼ぶ）。
15. **自動承認にしても、今月の上限だけは効かせる**（`settings.monthlyCapUsd`）。
16. **AIが動いていない成果を「AI生成」と記録しない**（来歴 `template`）。
17. **同じ本文を2か所に保存しない。** 提出物は `assembleResult(task)` で組み立てる。
18. **失敗した仕事を行き止まりにしない。** 押しても何も起きないボタンを出さない。
19. **席数の呼び名は `seatsPerGenre` だけ。**
20. **同じ関係を2か所に持たない。** 案件と仕事の結びつきは、仕事の側の `dealId` だけ
    （`deal.taskIds` は誰も書いておらず、AI費用が常に¥0になっていた）。
21. **費用の累計を操作履歴から数え直さない。** 古い記録は畳まれて消えるので、
    `settings.costTotalUsd` / `costMonthUsd` に積む。
22. **画面と実行で道具の判定を分けない。** `tools.isToolEnabled()` の1か所だけ
    （記録が無い＝使える）。
23. **在籍数の上限は持たない。** 端末内で動くだけなので人数を絞る理由が無い。
24. **読めないものを読めるふりをしない。** PDFは本文の貼り付けを案内する。
25. **取り込み（インポート）は必ず確認を出す。** 今のデータを置き換えると伝える。
26. **AIの失敗は「次にすること」まで書く**（`providers/stream.js` の `failureAdvice`）。
27. **台帳は手で更新しない。** 仕事から毎回導くビューにする。手で持つのは
    期限・次の対応・保留理由の3つだけで、置き場所は仕事の側（`task`）。
28. **回答の枠は最後の手順にだけ掛ける。** 1行で足りる調査結果に
    「①結論②最優先…」を付けない（`runtime.isFinalStep`）。
29. **判断・見出しは「提出物を書いた手順」の本文から拾う**（`workflow.finalOutput`）。
    全手順を連ねた `assembleResult` から拾うと、途中の手順の見出しが勝つ。
30. **引き継ぎで材料を消さない。** 枠が拾えなかった出力はそのまま全部渡す。
31. **CSV はセルを数式にさせない**（先頭が `= + - @` なら `'` を足す）。BOM を付ける。
32. **CSV から仕事は作らない。** 受付番号が一致した仕事の3列だけを書き換える。
33. **読めない日付で、いまの期限を消さない**（`ledgerCsv.parseDateCell`）。

これらはすべて `test/ouro.test.mjs` が機械チェックしている。

## 速さ（サクサク動かすための64の仕組み）

起動〜表紙 1642ms → 554ms → **395ms**、画面の切り替え 中央値 54ms → **27ms**、
画像 2.2MB → **176KB**、入力6文字あたりの保存 5回138KB → **1回1KB**
（CPU4倍スロットルでの実測）。**64項目**の内訳と「どこを直せばよいか」は
**[docs/PERFORMANCE.md](docs/PERFORMANCE.md)**。

```bash
npm run size   # 起動時に読む量が上限を超えていないか
npm run perf   # 起動の速さを測り、前回と並べる（合否は出さない）
```

特にハマりやすい点：

- **`content-visibility: auto` を `::before` で装飾している要素に付けない**
  （`.step` のタイムラインの点が切り落とされる）。
- **段階表示（先頭120件）と五十音バーの母数を混同しない** — バーは
  絞り込み結果の**全体**から作る。でないと120件の外へ飛べなくなる。
- **`REST_KEYS` は読み込みが済むまで保存しない** — 空配列のまま保存すると
  操作履歴が消える（`hydratedRef` / `preAuditRef` がこれを防いでいる）。
- **一部だけ読み込んだコレクションで、読んでいないレコードを消さない** —
  操作履歴は起動時に新しい400件だけ読む。`partialKeys` の印が外れた状態で
  手元の400件を保存すると、残りが全部消える。
- **同時に走る手順の引き継ぎ先を「g+1」で探さない** — 未雇用の役職を外すと
  番号が飛ぶので、残っている番号の中の次を探す。
- **窓表示（`Window.jsx`）の行の高さは JSX と CSS の両方をそろえる** —
  片方だけ直すと、行が増えるほど位置がずれて空白が出る。
- **全件の読み足しは順番を守る** — 仕事も起動時は新しい120件だけ読む
  （`useAllTasks`）。**`await flushNow()` → `load(..., 0, false)` → setState →
  `adoptFullList()`** の順。`save()` は呼んだ時点の配列を抱えて待っているので、
  順番を崩すと古い一部だけの配列があとから書かれ、読んでいないレコードが消える
  （実際に 300件 → 121件 まで減らした）。
- **読まなかった id は目録の末尾に付け直す**（`partialTail`）— 付け直さないと
  残りが消え、目録を書かないと新しく作った仕事が次の起動で消える。

## 開発

```bash
npm install
npm run dev       # 開発サーバー
npm test          # node --test（280件）
npm run build     # 本番ビルド
npm run preview   # ビルド結果の確認
```

- React 18 + Vite（JSX・TypeScript なし・**外部ランタイム依存なし**）
- 保存は IndexedDB（localStorage フォールバック）。`lib/storage.js` は
  ネットワークに一切触れない。
