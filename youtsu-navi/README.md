# 腰痛ナビ

セラピスト・整体師・有資格者が、施術中にお客様の状態を入力すると、
**安全トリアージ（レッドフラグ）** と **推定原因パターン・施術方針・ホームケア** を
提示する判断支援アプリです。腰痛から始まり、現在は **腰痛／肩こり・頸部痛／膝痛** の
3症状に対応しています（ホームで切り替え）。

公開URL: https://youtaix656-eng.github.io/-/youtsu-navi/

> 本アプリは医療機器ではなく、診断を行うものではありません。
> 表示される「推定パターン」「％」は診断名・診断確率ではなく、入力内容からの目安です。
> 最終的な施術判断は施術者本人が行うものとします。

## 現在のフェーズ（Phase 1 = 腰痛特化MVP）

企画書の「改善策 #8（初回リリースはスコープを絞る）」に従い、実装範囲を2機能に絞っています。

| 状態 | 機能 |
|---|---|
| ✅ | ① 症状入力 → 最適解提示（推定原因パターン・確率の目安・施術アプローチ・ホームケア） |
| ✅ | ② 安全トリアージ（レッドフラグ検知 → 施術中止／受診推奨アラート） |
| ✅ | 同意画面と同意履歴（改善策 #7）／資格別の業務範囲の出し分け（#4）／要配慮対象チェックリスト（#10）／根拠・出典管理（#1・#2）／ローカル保存のみ（#5）／汎用症状スキーマ（#6） |
| ✅ Phase 2 | カルテ・履歴管理（表示名のみ・端末内）、結果の書き出しと共有 |
| ✅ Phase 2 | 音声メモ入力（既定オフ・設定からオプトイン） |
| ✅ Phase 3 | 知識ベース構築（YouTube・書籍の取り込み、二段階チェック #3） |
| ✅ Phase 4 | 肩こり・頸部痛／膝痛への拡張（汎用スキーマをそのまま流用） |

## 使い方

1. 初回起動時に同意画面と資格選択（あん摩マッサージ指圧師／はり師・きゅう師／柔道整復師／整体師・セラピスト）。
2. ホーム →「新しく評価する」で8ステップの入力（安全確認 → 部位 → 性質 → 発症と経過 → 動作 → 神経症状 → 生活 → ペインスケール）。
3. 結果画面に、上から **安全トリアージ → 要配慮対象チェックリスト → 推定パターン（％の目安・根拠・施術方針・ホームケア）** の順に表示。

安全確認のステップで緊急のレッドフラグを選ぶと、入力途中でもその場でアラートが出ます。

### 目次（あ〜ん / A〜Z）に項目を足す時

目次はホーム／下部ナビの「📖 目次」から開き、項目をタップすると資料画面の該当箇所へ飛びます。
中身は `src/data/toc.js` が各データファイルから自動生成するので、目次側に一覧を書き写しません。
新しい項目を足す時は、元のデータ（`redFlags.js` / `patterns.js` / …）に次を足すだけです。

1. **タイトルは重複させない** — `tocTitle`（無ければ `name` / `title` / `category`）が目次の見出し。
   同じ文字列が2つあると `toc.test.mjs` の「目次のタイトルは重複しない」が落ちます。
2. **漢字を含むなら `reading` をひらがなで必ず書く** — 自動推定はしません（誤読をそのまま索引に
   出さないため）。書き忘れると「その他」に落ちるので、これもテストが検出します。
3. **数字は読み方で振り分けられる** — `reading` を省いても数字は `autoReading` が読みに変換します
   （例「20歳未満の方」→ にじゅう… → **な行**、「2019」→ にせんじゅうきゅう）。
   数字の見た目順で先頭に固まることはありません。
4. **アルファベットで始まる項目は A〜Z の枠**に入ります（英語の出典など）。
5. 飛び先は `TOC_CATEGORIES` のタブと `toc-<種別>-<id>` の anchor。資料画面側の要素に同じ id を
   付けておくこと（これもテストで検査）。
6. **①②③…のように番号順が意味を持つ項目**は `sortKey`（並べ替え専用の上書き）を付ける。
   行の振り分けは常に `reading` で決まり、`sortKey` は行の中の順番だけを変える。

### カルテ（Phase 2）の考え方

- **個人情報を持たない** — 識別は「表示名」（A様／田中T など20文字まで）のみ。氏名・連絡先・
  生年月日を入力させるUIは作らない。同じ表示名の記録が自動で経過としてまとまる。
- **保存しているのは入力（タグ）** — 判定結果そのものではなく入力を保存しているので、
  ロジックを直したあとでも過去の記録を最新の判定で読み直せる（`exporter.js` の `analyze`）。
- **お客様向けの書き出しは既定で推定パターン名を含めない** — 診断と受け取られるのを避けるため。
  含めたい時だけチェックを入れる（`homecareText(record, { includePatterns: true })`）。
- **バックアップはカルテだけ** — 設定・同意履歴は含めない。他アプリのファイル・壊れたファイルは
  `parseRecordsJson` が弾く。

### 音声メモ入力（Phase 2）の考え方

施術中は手が離せないので、カルテのメモ欄を話して入力できるようにしてある。

- **既定はオフ** — `settings.voiceInput`。設定画面でオンにした時だけメモ欄に
  「🎤 音声で入力」ボタンが出る（`canUseVoiceInput` が「設定がオン」かつ「端末が対応」を
  まとめて判定する。画面ごとに条件を書かない）。
- **プライバシー方針の明示的な例外** — 保存は端末内だけという方針は変えていないが、
  ブラウザの音声認識（Web Speech API）は多くのブラウザで**音声をブラウザ提供元のサーバへ
  送って**文字にする。つまりマイクの音声だけは端末の外に出る可能性がある。だから既定オフにし、
  設定画面とボタンの説明（`VOICE_PRIVACY_NOTE`）で仕組みをそのまま書いている。
  認識できた文字は他の入力と同じく端末内にしか残らない。
- **入力を奪わない** — 聞き取り中でもキーボード入力は止めない（誤変換をその場で直せるように）。
  確定した文字は `appendTranscript` で末尾に足す。日本語はそのまま連結し、英数字どうしの
  境目だけ半角スペースを入れる（「SLR test」／「SLR陽性」）。
- **マイクを掴んだままにしない** — 画面を離れる時は `abort()` で必ず止める。
- 新しい画面でメモ欄を作る時は `components/VoiceMemo.jsx` をそのまま使う
  （`label` / `value` / `onChange` / `settings` を渡すだけ。設定オフ・非対応端末では
  ただのテキスト欄として動く）。

### 知識ベース（Phase 3）と二段階チェック

動画・書籍・研修で学んだことを貯める場所。**見聞きしたことをそのまま提案に混ぜない**ための
仕組みを `src/lib/knowledge.js` に集約している（画面側でルールを作らない）。

- **段階（stage）** — `draft`（下書き）→ `checked`（第1チェック済み）→ `active`（運用中）。
  結果画面に出るのは **`active` だけ**。`rejected`（見送り）は消さずに理由ごと残す
  （同じ誤りを繰り返さないため）。
- **第1チェック** = 取り込んだ本人の自己チェック（出典を書いた／書き写しでなく自分の言葉／
  言い切っていない／業務範囲内）。
- **第2チェック** = 日を改めた裏取り（収録済みの出典と矛盾しない／**受診をすすめる判断を
  弱めていない**／一次情報か別の情報源で確認／診断と受け取られない言い方にできる）。
  **第1と第2で同じ観点をなぞらない**ことをテストで担保している。
- **`keepsRedFlag` は critical** — ここが外れたら運用に進めず自動で見送りになる。
  二段階チェックで一番守りたいのはこの1点。
- **日を改めることを促す** — `REVIEW_GAP_MS`（20時間）以内の第2チェックは止めはしないが
  「同じ日の見直し」として記録に残す。`dueForSecondCheck` がホームと一覧の「今日の見直し」を作る。
- **著作物を貯めない** — 要約は `SUMMARY_MAX`（600字）まで。長文の貼り付けは
  `validateNote` がエラーにする。出典（誰の・どの動画／本の・どこ）は必須。
- **言い切りの検出** — 「必ず治る」「〜と診断できる」などは警告として出す（保存は止めない。
  直すかどうかは本人が決める）。
- **結果画面での扱い** — `activeNotesFor` が推定パターン・タグ・症状のどれかに重なるメモだけを
  返す（重なりゼロなら出さない）。表示は `Result.jsx` の `KnowledgeNotes` で、
  **アプリが元から持つ根拠とは別カード**にする（施術者自身が集めた情報だと分かるように）。
- 見出しは目次と同じ規則（**重複禁止・漢字を含むなら読み必須**）。一覧は `buildKanaIndex` で
  あ〜ん / A〜Z に並ぶ。ただし知識ベースは端末内のユーザーデータなので、静的な `toc.js` には混ぜない。
- バックアップはカルテとは**別ファイル**（`knowledgeFileName`）。段階もそのまま引き継ぐ。

### ロジックを直す時

- 判定は**すべてタグ経由**。入力UIを変えても `patterns.js` / `redFlags.js` は書き換え不要。
- 新しいタグを使う時は `schema.js` の `TAG_VOCABULARY` に追加する（未登録タグはテストが落ちる）。
- 医療内容を足す時は、必ず `sourceIds` で出典を紐づける（根拠のない提案を出さない方針）。
- 毎年変わる数字・解釈が分かれる事項には「※要確認」を付ける。

## 開発

```bash
npm install
npm run dev      # 開発サーバ
npm test         # ロジックのテスト（node --test）
npm run build    # dist/ へビルド（GitHub Pages のサブパス配信のため base: './'）
```

リポジトリ直下の `npm test` からも同じテストが実行されます（`node --test` の再帰探索）。
デプロイは `main` への push で `.github/workflows/deploy.yml` が
`/youtsu-navi` サブパスへ配置します。
